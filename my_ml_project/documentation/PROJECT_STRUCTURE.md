# Project Structure

This document explains how `my_ml_project/` is organized, what every folder
and important file is for, and how the pieces connect into one reproducible
pipeline: **dataset → training → model → API/web view → evaluation/audit →
thesis report**.

If you are new to this project, read this file first.

---

## 1. Folder-by-folder overview

```
my_ml_project/
├── dataset/            # Original dataset and sample API request bodies
│   ├── raw/             # The one and only source dataset (do not edit)
│   └── samples/         # Example JSON payloads for testing the API
├── src/                 # Core ML pipeline — training, comparison, serving
├── models/              # Final trained model artefacts (output of src/train_model.py)
├── evaluation/           # Independent audit scripts (cross-validation, overfitting,
│                          #   explainability, error analysis) — read-only w.r.t. src/
├── results/             # JSON outputs produced by the evaluation/ scripts
├── webapp/              # Local browser front-end for the API
├── report/              # Thesis/book documents and the script that edited them
├── documentation/       # This file, the project README, and the code-walkthrough guide
├── requirements.txt     # Full list of Python packages the project depends on
├── .gitignore
└── .venv/               # Local virtual environment (not tracked by git)
```

Everything under `dataset/`, `models/`, `results/`, and `report/` is
**generated or provided data** — nothing in those folders should be hand-edited
except by re-running the corresponding script. Everything under `src/` and
`evaluation/` is **source code**.

---

## 2. `dataset/` — the dataset and sample requests

| File | What it is |
|---|---|
| `dataset/raw/student_career_success_dataset.xlsx` | **The original dataset.** 50,000 rows × 29 columns, the "Student Career Success Prediction Dataset" from Kaggle (Fatimah, 2026). This is the *only* copy of raw data in the project — there is no separate "processed" dataset file, because cleaning/feature-engineering happens **in-memory** inside `src/train_model.py` every time it runs (see Section 3). Do not edit this file; if you need a different dataset, replace it here and everything downstream will re-derive from it automatically. |
| `dataset/samples/employable.json` | Example request body for a strong profile — used to sanity-check the API's "Employable" path. |
| `dataset/samples/employ_body_request.json` | A second, similarly strong example request body. |
| `dataset/samples/not_emoloyable.json` | Example request body for a weak profile — used to sanity-check the API's "Not Employable" path and its gap-analysis output. |

**Why `.xlsx` and not `.csv`:** the project originally used a CSV export of
this dataset; both formats were verified byte-identical (same 50,000 rows,
same 29 columns, zero differing cells) during the ML audit, so the CSV was
removed to avoid keeping two copies of the same data. All scripts read the
`.xlsx` file directly via `pandas.read_excel`.

---

## 3. `src/` — the ML pipeline (training, comparison, serving)

This is the **canonical, reproducible pipeline**. Everything the thesis
reports as "the model" comes from these three files.

| File | Role | How to run it |
|---|---|---|
| **`train_model.py`** | **THE training script.** Loads `dataset/raw/student_career_success_dataset.xlsx`, cleans it, engineers two composite features (`Overall_Preparedness_Index`, `Skills_per_Project`), excludes 6 demographic/contextual columns, splits 80:20 (stratified, seeded), preprocesses inside a scikit-learn `Pipeline` (median/mode imputation, scaling, one-hot encoding), tunes an `XGBClassifier` via `RandomizedSearchCV`, evaluates once on the held-out test set, and saves the final pipeline. | `python src/train_model.py [optional_path_to_dataset]` |
| **`compare_algorithms.py`** | Trains Logistic Regression, Decision Tree, Random Forest and XGBoost under the identical split/preprocessing protocol, for the thesis's Table 5.6 algorithm comparison. Does not overwrite the saved model. | `python src/compare_algorithms.py [optional_path_to_dataset]` |
| **`main.py`** | The FastAPI serving layer. Loads the two files in `models/` and exposes `GET /` and `POST /predict`. Applies the same feature engineering as training, at inference time, on submitted profiles, then returns a verdict, probability, and (for at-risk predictions) a rule-based list of improvement gaps. | `uvicorn main:app --app-dir src --reload` |

**Default dataset path:** all three scripts default to
`dataset/raw/student_career_success_dataset.xlsx` (resolved relative to the
project root, regardless of your current working directory), and all three
accept an optional first command-line argument to point at a different file.

---

## 4. `models/` — the final trained model

| File | What it is |
|---|---|
| **`best_employability_pipeline.pkl`** | **The final, submission-ready model.** A fitted scikit-learn `Pipeline` (preprocessing + tuned `XGBClassifier`) produced by `src/train_model.py`. This is the one and only model artefact the API (`src/main.py`) loads at startup. |
| **`label_encoder.pkl`** | The fitted `LabelEncoder` that maps `Employable` ↔ 0 and `Not Employable` ↔ 1, saved alongside the model so predictions can be decoded back to human-readable labels. |

Both files are regenerated by re-running `src/train_model.py` — they are
build artefacts, not something to hand-edit. Because `random_state=42` is
fixed throughout the pipeline, re-running training reproduces these files
byte-for-byte-equivalent in their predictions (verified during the reorganization: accuracy 0.8170, ROC-AUC 0.8068, identical confusion matrix and feature-importance ranking to six decimal places, both before and after this restructuring).

## 5. `evaluation/` — independent audit and validation scripts

These scripts do **not** change the model or the training methodology. They
were written during a senior-level ML audit of the project to validate,
stress-test, and explain the model that `src/train_model.py` already
produces. Each one loads the dataset itself via `phase2_common.py` (a
faithful copy of `train_model.py`'s cleaning/feature-engineering logic, kept
separate so the audit never depends on — or risks modifying — the
production training script).

| File | What it checks | Output |
|---|---|---|
| `phase2_common.py` | Shared helper: dataset loading/cleaning, `X`/`y` construction, preprocessor builder. Not a script — imported by the other four. | — |
| `cross_validation_analysis.py` | Stratified 5-fold cross-validation (on the full dataset and on the training partition alone) for all compared algorithms, to confirm the reported test-set numbers are not a lucky split. | `results/phase2_cv_results.json` |
| `hyperparam_validity_check.py` | Reproduces `train_model.py`'s exact `RandomizedSearchCV` result, then re-runs a much wider search to confirm the original search budget was sufficient. | `results/phase2_hyperparam_results.json` |
| `multiseed_stability_check.py` | Re-fits the tuned model at four additional random seeds to measure how much the reported test accuracy/AUC depends on the particular train/test split. | `results/phase2_multiseed_results.json` |
| `overfitting_and_explainability_analysis.py` | Train-vs-test-vs-CV gap analysis (overfitting/underfitting check) for all four algorithms; native vs. permutation feature importance; false-positive/false-negative error analysis, including an audit-only cross-tabulation against the excluded demographic columns (Major, Gender, University_Year) for fairness. | `results/phase2_overfit_explain_results.json` |

**Findings from these scripts are already written into the thesis** (Section
5.7.1, Table 5.6, Section 5.10, and Section 5.14 of `report/Main-Book.docx`
and `report/Report-02-UPDATED.docx`) — the scripts and JSON files here are
the reproducibility trail behind those numbers, not a separate, unfinished
piece of work.

## 6. `results/` — audit output data

Plain JSON files, one per `evaluation/` script, containing every raw number

native and permutation importances, error-analysis cross-tabs) referenced in
the thesis's cross-validation and explainability sections. Regenerate any of
them by re-running the corresponding script in `evaluation/`.

## 10. Which dataset is "original" vs. "processed"?

There is only **one** dataset file in this project:
`dataset/raw/student_career_success_dataset.xlsx`. There is no separate
processed/cleaned file on disk — cleaning (deduplication, whitespace
stripping, target-label normalisation), leakage-column removal, and feature
engineering all happen **inside `src/train_model.py` at run time**, so the
"processed" version is always freshly and identically derived from the one
raw file. This was a deliberate reproducibility choice: there is no risk of
the raw and processed files drifting out of sync, because there is only ever
one source of truth.

## 11. Which script is "final" vs. "experimental"?

- **Final / production:** `src/train_model.py`, `src/compare_algorithms.py`, `src/main.py`. These define the actual, reported methodology and are what the thesis describes.
- **Audit / validation (not experimental drafts — completed, one-purpose analyses):** everything in `evaluation/`. These were written to stress-test the final model, not to explore alternative methodologies; their results are already incorporated into the thesis text.
- **Archived:** none. No outdated or duplicate code paths remain in the project after this reorganization — earlier one-time editing scripts used to build the thesis document (`update_thesis.py`, `add_webview_section.py`, `generate_dataset_figures.py`, `generate_diagram_figures.py`, `replace_figures.py`) were already removed in a prior cleanup pass once their one-time edits had been applied and committed; only `phase3_apply_findings.py` remains, in `report/`, since it is directly relevant to auditing the thesis text it produced.

## 12. Which files generate the thesis's figures and tables?

The six regenerated figures (3.1, 3.2, 4.2, 4.3, 5.1, 5.2) and the webview
screenshots embedded in the thesis were produced by one-time generation
scripts that have since been removed after their output was embedded
directly into the `.docx` files (see Section 11) — the figures themselves
live only inside `report/Main-Book.docx` and `report/Report-02-UPDATED.docx`
now, not as standalone image files in this repository. Table 5.6 (algorithm
comparison) is produced by `src/compare_algorithms.py`; Table 5.7 (feature
importance) and the Section 5.7 classification report/confusion matrix come
directly from `src/train_model.py`'s console output; the new Section 5.7.1
cross-validation table and Section 5.14 error-analysis figures come from the
`evaluation/` scripts via `results/*.json`.

## 13. Which files are directly tied to the final research results?

`src/train_model.py` → `models/*.pkl` → the numbers in Table 5.5 (accuracy
0.8170, ROC-AUC 0.8068, confusion matrix `[[7391,417],[1413,779]]`) and
Table 5.7 (feature importance). `src/compare_algorithms.py` → Table 5.6.
`evaluation/*.py` → `results/*.json` → Section 5.7.1 and the fairness/error
findings in Section 5.14. All of these numbers are cross-referenced and
verified consistent with each other and with the thesis text as of the last
full audit pass.

## 14. Which files are archived, and why?

None, as of this reorganization. All files present in the project are
either (a) part of the live, reproducible pipeline, (b) the dataset, (c)
the completed audit trail, or (d) the thesis/documentation. Files that were
genuinely one-off and no longer needed (old pre-fix model/API copies, one-time
docx-figure-generation scripts, a stray CSV duplicate of the dataset, Word
lock files, Python bytecode caches) were identified and removed during this
and earlier cleanup passes rather than moved to an `archive/` folder, since
keeping a project free of dead weight was judged clearer than preserving
files nobody will reopen. If you want a safety net for anything before
deleting it yourself in the future, git history retains every prior version
regardless.

## 15. End-to-end reproduction checklist

```bash
# 1. Set up the environment (once)
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt

# 2. Train the model (reads dataset/raw/, writes models/)
.venv\Scripts\python src\train_model.py

# 3. Run the algorithm comparison (Table 5.6)
.venv\Scripts\python src\compare_algorithms.py

# 4. Run the audit suite (writes results/)
.venv\Scripts\python evaluation\cross_validation_analysis.py
.venv\Scripts\python evaluation\hyperparam_validity_check.py
.venv\Scripts\python evaluation\multiseed_stability_check.py
.venv\Scripts\python evaluation\overfitting_and_explainability_analysis.py

# 5. Serve the API
.venv\Scripts\python -m uvicorn main:app --app-dir src --host 127.0.0.1 --port 8000

# 6. Open the web view
#    (with the server above running) open webapp\webview.html in a browser
```

Every step above was re-verified to work from these exact paths after the
folder reorganization that produced this document.
